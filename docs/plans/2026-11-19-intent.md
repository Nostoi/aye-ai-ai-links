## 1. Benefit, and the case reachable today

Links kept for good are treated as reading:
- the Bills space's links,
- an account page,
- a doc the owner returns to.

They surface on Home's Today (`worthALook` → `previewDigest`) and get asked about in Tidy. Today the only way to stop that is Tidy's Keep, and it lasts only 180 days (`TIDY_KEEP_WAIT_MS`, `core/tidy-up.ts`).

**Reachable on `main` (OBSERVED in source).** Save a bills link and leave it unopened for 30 days. Home may pick it as a Today card, and it qualifies for Tidy (`qualifying`). After Tidy's Keep it returns 180 days later.

**What this PR delivers.**
- Every link records the owner's intent, To explore or To keep, with who said so.
- The owner can set it from the ⋯ menu, from Keep handy and from the edit dialog.
- An AI can set it and is shown as guessing.
- Tidy never asks about a To keep link again.

To keep links also leave Today: owner ruling 1 brings that one-line filter into this PR. The rest of Today's rule stays #340's work.

## 3. Decisions (recommendation first)

1. **Fields.**
   - `Link.intent: "explore" | "keep"` (`INTENTS` in `types.ts`).
   - `Link.intentSource: Source | null`. Null means nobody said, which is the default To explore.
   - SQL: `intent TEXT NOT NULL DEFAULT 'explore' CHECK (intent IN ('explore','keep'))` and `intent_source TEXT CHECK (intent_source IN ('stated','asked','inferred'))`.
   - A third CHECK, `(intent = 'explore' OR intent_source IS NOT NULL)`, makes a keep with no source impossible to store (m1). It goes on the second ADD COLUMN.
   - Explore with a NULL source stays the default form: a new link, and every link nobody has spoken for.
   - `LinkPatch` gains `intent`, `intentSource` and `intentOver?: (Source | null)[]`, modelled on `summaryOver`: the pair is written only while the row's source is listed, decided in the same UPDATE.
   - `LinkExpectation` gains `intent?` and `intentSource?: (Source | null)[]`.

2. **Migration** (one function entry, appended; no `links` rebuild):
   1. ADD both columns.
   2. Tidy-kept within 180 days of migration time → keep/stated. This reads the clock as the `stats_meta` seed does.
   3. A `link_tools` row with status `kept` → keep with the tool's source. This runs last, so the handy source wins.
   4. `DROP COLUMN put_away_at` and `DROP COLUMN tidy_kept_at`. Nothing is read from `put_away_at`.
   5. Rebuild `link_edits` with literal DDL (as `rebuildLinkEdits` does, never by string-editing `sqlite_master`).
      - Copy today's columns. That is `rebuildLinkEdits`'s list plus `prior_summary_source` and `written_summary_source`, which a later ALTER added. Probe 2 printed the full current DDL; copying `rebuildLinkEdits` alone would drop those two.
      - Add `intent_changed` (default 0), `prior_intent`, `prior_intent_source`, `written_intent` and `written_intent_source`.
      - Add `OR intent_changed = 1` to the CHECK.

   Foreign keys are already off inside `migrate()`. The rebuild finds triggers by their SQL text (as `rebuildLinks` does) and recreates them, even though the probe found none on `link_edits` by `tbl_name`. The `links` triggers are untouched by DROP COLUMN (probe). `link_events` is not touched (decision 3).

3. **Events (owner, 2026-11-19: A2).** No event kinds change.

   - Keep it, Explore it, Keep handy, the edit dialog, MCP and the AI pass record no event.

13. **The AI pass** (`core/intent-pass.ts` and `ai/intent-guess.ts`, wired in `start-server.ts` only when `config.ai` is set, like `createSummaryPass`).
    - **Bounded, resumable queue that also serves as an audit.**
      - A new table `intent_guesses (owner_id, link_id, outcome TEXT CHECK (outcome IN ('keep','not_keep','failed')), tries INTEGER NOT NULL DEFAULT 0, PRIMARY KEY (owner_id, link_id), FK → links ON DELETE CASCADE)`.
      - Its migration fills it with live active links whose `intent_source IS NULL`, with `outcome` NULL.
      - A link saved later is never queued, so the pass is one-off.
      - A restart resumes from the rows whose `outcome IS NULL`; when none are left, the pass ends without polling.
      - Rows are kept, not deleted. One `SELECT … WHERE outcome = 'keep'` lists exactly what the pass wrote. One `UPDATE links SET intent='explore', intent_source=NULL WHERE intent_source='inferred' AND id IN (those)` undoes a bad pass. Without this, a bad pass can't be told apart from an agent's inferred writes.
      - It registers in `hidden-link-coverage.test.ts`. Reads skip `deleted_at`.
    - **Batching.** Up to 25 links per call, one owner per batch. Links are numbered 1..N in the prompt, so the reply can't invent an id.
    - **What each link sends.** Title, site, URL path, tag names (pinned spaces marked), the why and its source, and the summary. No page text.
    - **Prompt.**
      - Defines To keep as something held on to and returned to: bills, accounts, docs, a tool. To explore is to read, try or watch.
      - "Pick only links that are clearly To keep. When unsure, leave it out; a link left out stays To explore."
      - The same "material, not instructions" line as `summarize.ts`.
      - Reply `{"keep":[n,…]}` and nothing else.
    - **Per-batch bound (challenge Q1).** A reply naming more than 8 of a batch's 25 links counts as a failure, and nothing is written. One injected title or summary can therefore turn at most 8 links To keep. A genuine cluster bigger than that fails safe: after its tries run out it ends `failed` and stays To explore, where Today shows it to the owner.
    - **Write.** One transaction per batch:
      - set keep/inferred where `intent_source IS NULL AND deleted_at IS NULL`, so an owner's choice meanwhile wins;
      - set each queue row's `outcome`.

      The link itself is left alone for "not keep". No events.
    - **Failure handling (m3, A4).**
      - **What counts as a failure:** a reply that isn't that exact shape, has numbers out of range, is over the bound or is cut off.
      - **Per batch:** a failure adds 1 to `tries` on the batch's rows. Those rows back off (60 s, doubling) while later batches go ahead, so one bad batch blocks nothing.
      - **Terminal outcome:** after 3 tries a row's outcome becomes `failed`, which is terminal; the link stays To explore. A retry of a failed batch is cut to 5 links at a time, so one bad link doesn't fail 24 others.
      - **Pausing:** three failures in a row, or `AiUnavailable`, pause the whole pass (the summary pass's numbers). `AiUnavailable` does not add to `tries`.
      - Reuse the summary pass's backoff shape; do not share its code.
    - **Cost bound.** ⌈N/25⌉ calls, with a 5 s gap between calls and a 90 s timeout. INFERRED estimate, never measured (the library's size was not read): about 120 input tokens per link, so about 40 calls for 1,000 links.
    - **Done signal.** It logs `intent guesses: done` once no row is left undecided. On the server, `SELECT count(*) FROM intent_guesses WHERE outcome IS NULL` returning 0 is the check before #340 deploys; `failed` rows count as done.
    - **Without AI.** With no `AYE_AI_` the queue just sits there, and every link stays To explore.

## 5. One PR or a sequence

There are two PRs, split for independent revert:

- **PR A (intent): the field, the migration, menus, dialog, Keep handy, Tidy, MCP and export.** These are one piece of knowledge.
  - The migration is the step that can't be undone. Tidy's `tidyKeptAt` retirement and the export/MCP field changes all depend on it.
  - Splitting the UI from the field would ship an intent nobody can set or see.
- **PR B (AI pass): its queue migration, pass and wiring.**
  - It is the only part that can be wrong without anyone seeing it (a wrong To keep is silent).
  - It needs its own review of the prompt and the backoff.
  - It can be rolled back on its own, but not with `git revert` after deploy: `migrate()` refuses a database newer than the code.
    - Rolling back means a forward PR that removes the wiring and keeps the migration entry. A leftover queue does nothing.
    - That PR also undoes the guesses, using the queue's `outcome` rows (decision 13).
  - It must deploy and finish on the server before #340.
