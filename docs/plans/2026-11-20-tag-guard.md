# Keep the owner's tags from an AI's guess (#354) Implementation Plan

> Steps use checkbox (`- [ ]`) syntax. Write each test red first and confirm it fails on behaviour.

**Goal:** An AI's guessed tag list never removes, renames or relabels a tag the owner gave. The owner's ruling (2026-11-20, on #354): "keep yours", mirroring #342 — an AI's guessed list may add guesses and remove its own guesses; every tag the owner gave (stated/asked) stays; removing or changing one of the owner's tags needs the AI to say the owner asked; an owner's tag never turns into a guess.

## Grounding

- **Benefit (reachable today):** MCP `update_link` (`src/mcp/server.ts`, schema `tags: tags.optional()`) and the in-app Ask AI chat (same tools in process) reach core `updateLink` (`src/core/links.ts`), where `if (tags !== undefined) patch.tags = normalizeTags(tags);` builds a patch with no source check; `SqliteStore.updateSync` then deletes all the link's `link_tags` rows and attaches the new list (`src/store/sqlite-store.ts`, after the guarded UPDATE). OBSERVED. The #352 design challenge reproduced it: a stated `meetings` disappears when `update_link` sends inferred `[productivity]`.
- **Who asks (PROPOSED_NEW):** the tag list is a set, so "the owner asked to remove X" can't be read from one tag's source. `update_link` gains an optional `tagsSource: "stated" | "asked" | "inferred"`: who decided this tag set. Absent or `"inferred"` → a guess, guarded. `"stated"`/`"asked"` → the owner's own set, replaced as today. This mirrors the why's `{text, source}`. Each tag's own `source` keeps its meaning (who gave that tag).
  - Rejected: reading the owner's say from "any tag in the list is stated/asked" (an AI copying the owner's existing tags with their sources would silently gain the right to drop one); refusing all AI changes to owner tags (the owner ruled that an AI acting on their request may).
- **The rule (core decides, store applies atomically).** For the sent set S and the link's current tags C at write time:
  - **Both modes:** a key in both C and S keeps the stronger source (`strongerSource` in `src/core/tags.ts`), so an owner's tag never turns into a guess, even on the owner's-say path, and a guess sent as stated for an inferred tag becomes stated.
  - **Guess** (no `tagsSource`, or `"inferred"`): every tag in C whose source is stated/asked stays (name, source, kind); inferred tags of C not in S are removed; new keys in S are added as given. Order: tags that remain keep their current relative order, new keys follow in S's order, so a guess never moves the owner's space (`linkSpace`, first pinned tag in order, `src/core/link-space.ts`).
  - **Owner's say** (`tagsSource: "stated"`/`"asked"`): S replaces the set in S's order, as today, except for the stronger-source rule above.
  - The merge happens inside the store's write transaction against the tags read there (as `whyOver`/`intentOver` decide atomically). Core sends `patch.tags` plus `patch.tagsGuess: true` for a guess. In SQLite the merge lives in the private `updateSync`, which `update`, `updateIf` and `updateWithReceipt` all funnel into inside one transaction (OBSERVED by the challenge); in FakeStore in `update`, which `updateIf` and `updateWithReceipt` delegate to. One pure helper in core (e.g. `mergeTags(current, sent, guess)` in `src/core/tags.ts`) computes the result; both stores call it, so the rule lives once.
  - `tagsGuess` is added to the `UpdateLinkInput` Omit list (`src/core/links.ts`), so callers cannot set it.
- **Door order:** MCP `update_link` pre-checks every refusal `updateLink` can make before it writes `handy` (`src/mcp/server.ts`, comment above `applyHandy`); the new `tagsSource` refusals join that pre-check, so a bad call writes nothing.
- Design challenge: `.claude/reviews/solution-choice-e2c736e….md`, run by a fresh Opus reviewer because Codex was out of credits (CROSS_MODEL_CHALLENGE_UNAVAILABLE: context-independent, same model family). Verdict REVISE; all five objections are taken into this plan.
- `save_link` is unchanged: a new link has no owner tags yet; a repeat save discards tags (OBSERVED, guidance line "the tags you sent are discarded").
- Owner paths are untouched: Edit link (`applyEdit`), Save (`addTags`, #352) and tag rename/merge/delete do not go through `updateLink`'s tag patch.
- Guidance (`src/mcp/guidance.ts` `UPDATE_LINK`, 2048-character cap, tested in `src/mcp/guidance.test.ts`): say that a guessed tag set keeps the owner's tags; to remove or change one at the owner's request, send `tagsSource: "stated"` (or `"asked"`).

## Non-goals

No change to tag rename/merge/delete tools (`merge_tags` and `delete_tag` already say to act only when the owner asks or confirms; they change a tag on every link, not one link's set), to `save_link`, or to the web dialogs. No guard on `kind` beyond what a kept tag already keeps. The ROADMAP entry states this scope.
