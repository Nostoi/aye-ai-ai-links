# Tidy up Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let the owner let go of old links without losing them. This plan adds a **Put it away** state that comes back when a newer focus entry fits it, renames **I'm done with it** to **It's stale**, and adds a five-link **Tidy up** session.

**Architecture:**
- Put-away is *archived plus a date*. `links.state` stays `active | archived`, and a new nullable `put_away_at` column marks an archived link as put away rather than stale. Existing `state === "active"` filters keep a put-away link out of lists, digests and Worth a look.
- The marker's meaning is owned by one core rule: every write that sets `state` decides `putAwayAt`. Only `putAwayLink` sets it, and every other state write clears it. This covers the web, MCP `update_link` and the in-app AI alike.
- Coming back is evaluated when Worth a look or the digest is built, as the spec says. It is read-only, so Home still marks nothing. A put-away link counts as back while a focus entry newer than its `putAwayAt`, inside the focus window, keyword-matches it. It then becomes a candidate with a `came_back` reason. It stays archived, out of the lists, until the owner engages: recording an opening of it, or **Bring it back**, makes it active.
- The Tidy up queue and session rules live in `core/`; the web page only shows them.

**Tech Stack:** TypeScript, Hono, SQLite (better-sqlite3), vitest, linkedom, biome. Node 22.

**Spec:** `docs/specs/2026-10-21-tidy-up-design.md` (visual reference `docs/design/tidy-up-mockup.html`). Issue #198. The cross-model challenge that revised this plan: verdict REVISE at 4fc2eb0, all eight objections accepted (see "Spec deviations" and Part 2).

## Spec deviations (decided at planning, recorded on #198)

1. **What "back" means.** The spec's Claude call said a matched link "is active again: back in its lists". Here a matched link comes back to Worth a look, the digest and search. It returns to the lists only when the owner opens it or chooses Bring it back. The reasons:
   - The match is evaluated read-only at build time, as the spec says. That covers links matched later, links whose text changes, and more matches than a cap, which a one-time write can't.
   - Home never writes on a view.
2. **Search fading.** The spec says "only stale links fade" in search. Search results fade nothing today, and this plan leaves search unchanged, so put-away links already "rank normally, never faded". The owner never asked for fading, so this deviation is reported to them.
3. **Handy tiles.** A Handy tile's ⋯ menu gets It's stale, but not Put it away. A kept tool is not reading, so a returned tool would be excluded from reading picks and could never come back.

## Review Focus

1. **A link put away *after* a matching focus entry exists must not come back from that entry.** Only entries created later count. Tested in Task 2.3.
2. **A late Undo must not reverse a newer decision.** Undo names the action it reverses. Undo of Put it away expects the exact `putAwayAt` it set. Undo of It's stale expects `putAwayAt` null. The sequence put away (tab A) → stale (tab B) → A's Undo is a conflict. Tested in Task 2.2.
3. **Stale through MCP must clear the marker.** `update_link {state: "archived"}` on a put-away link leaves `putAwayAt` null, so the link never comes back. Tested in Task 2.2.
4. **A Tidy up session whose queue shrinks under it.** Another tab, or an AI, acts on one of the five. The page refuses cleanly (409 shows the reload message) and does not double-act. Tested in Task 3.3.
5. **An inferred focus and no current focus.**
   - With an inferred focus, the fit line and Home's came-back reason say "(a guess)".
   - With no current focus, there is no fit line and no empty box, and Put it away is still offered.
   - Tested in Tasks 2.4 and 3.2.

```ts
export type DigestReason = /* existing */ | { kind: "came_back"; focus: FocusEntry; putAwayAt: Date };
```

A put-away link is a came-back candidate when all of these hold:
- a focus entry inside `FOCUS_WINDOW_MS`, created after its `putAwayAt`, finds it in `keywordSearch(owner, focus.text, { state: "archived" }, linkCount)`;
- it is not snoozed;
- it hasn't been surfaced since `putAwayAt` within `SURFACE_COOLDOWN_MS`. Surfacing before it was put away doesn't count.

The search limit is the whole library (`linkCount`, as `focusReasons` passes it). Filter to put-away links first, then cut to at most `FOCUS_MATCHES_PER_ENTRY` per entry per build. Cutting before filtering would let stale hits crowd out a put-away one. Came-back candidates take the focus slots ahead of `focus_words` links. Being evaluated on every build, a capped or later-matching link gets its turn on a later build.

```ts
export const TIDY_SESSION = 5;
export const TIDY_KEEP_WAIT_MS = 180 * DAY_MS;
export type TidyLink = { link: Link; gone: boolean; fit: FocusEntry | null };
/** Up to `limit` old links: gone first (earliest flagged), then oldest saved, then lowest id. */
export async function tidyQueue(deps: TidyDeps, owner: OwnerId, limit: number): Promise<TidyLink[]>;
/** Keep: sets tidyKeptAt = now while the link is active. */
export async function keepInTidy(deps: TidyDeps, owner: OwnerId, id: string): Promise<void>;
/** Whether Home offers Tidy up: at least TIDY_SESSION links qualify. */

```

`TidyDeps = { store, tools, checks, profile, keywordSearch, now }`, the same parts `DigestDeps` uses. A link qualifies when all of these hold:
- it is active;
- it is old by Global Constraints;
- it is not a kept tool;
- `tidyKeptAt` is null or at least 180 days ago.

`fit` is the newest focus entry in the window whose keyword search returns the link. It is null when there are no current entries or nothing matches.
