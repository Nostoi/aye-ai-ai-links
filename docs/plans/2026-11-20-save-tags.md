# Tags in the Save dialog (#352) Implementation Plan

> **For agentic workers:** Steps use checkbox (`- [ ]`) syntax. Write each test red first and confirm it fails on behaviour.

**Goal:** The Save dialog has an optional Tags field under the why (S1). A new link is saved with those tags; a repeat save adds the ones the link doesn't have yet and says which it added and which it already had.

**Spec:** `docs/specs/2026-11-20-why-and-tags-dialogs-design.md` (#352 parts), mockup `docs/design/why-and-tags-mockup.html` (S1, "S1 while typing", the "already saved, tags added" card). Owner rulings on #352 (2026-11-20).

## Grounding

- **Benefit (reachable today):** a link saved from the web page (top bar Save, phone menu, the bookmark's `/save`) gets no tags; the owner must open Edit link afterwards. After this, one Save files it. OBSERVED: `saveBody` in `src/web/http.ts` takes only `url`, `title`, `why`; `SavePageInput` (`src/core/save-page.ts`) has no tags.
- New link: `saveLink` already takes `tags` (`SaveLinkInput.tags`, `normalizeTags`) and stores them with the link in `insertIfAbsent` (OBSERVED, `src/core/links.ts` `saveLink`). A repeat save today discards tags (`saveLink` only fills a missing why on `!result.created`; OBSERVED).
- Repeat save (PROPOSED_NEW): one new owner-scoped store method, `addTags(owner, id, tags: LinkTag[]): Promise<{ link: Link; added: string[] } | null>`, on the link store (both `SqliteStore` and `FakeStore`, shared contract tests). In one transaction it attaches each tag whose key the link lacks, as given (core normalizes the names with `normalizeTags`, source `stated`), leaves every tag the link has (name, source, kind) alone, keeps the catalog's existing name/kind for a key it already knows, as a new link's tags do, and returns the link as it now is and the keys it added (in order). Null for an absent, foreign or deleted link. It writes no edit receipt, so an earlier edit's Undo still works; the addition has no Undo of its own (the owner removes a tag in Edit link).
  - Rejected after the design challenge (`.claude/reviews/solution-choice-f678297….md`): `editLink` with a retried compare-and-set. Retries can run out with the owner's tags unsaved, and its receipt replaces the link's latest edit receipt, so an Undo already on screen conflicts. Also rejected: `updateLink` with the full set (read-then-write that can drop a tag added meanwhile); a `tags` field on `LinkExpectation` (widens a shared contract for one caller).
- Search and the catalog read tags from the same tables (OBSERVED in the challenge: search, catalog, MCP reads and export need no new state). The implementer confirms `addTags` keeps the keyword index and the tag catalog in step the way `insertIfAbsent`/`update` do for tags (same triggers or the same helper), with a contract test that a tag added this way is found by tag filter and listed in `/tags/names`.
- "It already had" names only the typed tags the link already had, not all its tags.
- Typed tags are the owner's: `stated`. Names go through `normalizeTags`/the tag rule in core; the route caps each name at `EDIT_MAX_TAG_TEXT` like the edit route.
- `/save` stays signed-in and keeps no `ask` (spec constraint). The dialog fetches `/tags/names` (signed-in GET, same origin) for suggestions, as Edit does once per open; the `/save` GET still reads no owner data.

## Non-goals

No tag removal from Save; no change to the why in Save.

## Edit link… on the "already saved" view (owner, 2026-11-20: "Yes add it", as the mockup's card shows)

- The found view gains an **Edit link…** button beside Open it, shown only on a page that has the Edit dialog (`#edit-link`; OBSERVED it is mounted by All links, the space and search pages, Home, and with `{ panel: true }` wherever the Ask AI panel is, `src/web/page.ts` `scriptsFor`). Elsewhere, including the bookmark's `/save` page, it is hidden.
- Pressing it closes the Save dialog and opens Edit link on that link, filled as from its card. The edit dialog today opens only from a card's ⋯ menu (`edit-dialog.ts`, `card-menu button[data-act=edit]`) or a panel card. The implementer picks the smallest seam: e.g. `savedJson` carries the link's `editData` attributes (the one helper in `src/web/edit-link.ts`) so the found view is the card the dialog reads and redraws, opened through one new entry the edit script exposes. A Save in Edit then redraws the found view's title/why in place, or the found view simply closes.
- Tests: the button shows with `#edit-link` and is hidden without it; pressing it opens Edit link with that link's title, why and tags; Save there writes that link.

## Answer shape

`savedJson` gains `tagsAdded: string[]` (names added on this save, in order) and `tagsHad: string[]` (typed names the link already had, as the link names them). For a new link `tagsAdded` is every tag saved, `tagsHad` is empty.

## Tasks

### Task 1: Core — savePage takes tags

**Files:** `src/core/save-page.ts`; tests in `src/core/save-page.test.ts` (new) using `FakeStore` (it implements both the link store and `applyEdit`), plus one SQLite case through `src/deps.ts`'s stores if a store-contract file suits better (`src/core/store-contract.ts` `describe("savePage")` has the existing cases; its `deps()` needs `edits`).

- `SavePageInput.tags?: string[]`; `SavedPage` gains `tagsAdded`, `tagsHad`.
- New link: pass `tags: names.map((name) => ({ name, source: "stated" }))` to `saveLink`.
- Repeat save with tags: `addTags` as in Grounding. A tag-only repeat save with no why works; a repeat save with a why still runs the why rules first, then the tags.
- Files also: `src/core/store.ts` (the method on the link store interface), `src/store/sqlite-store.ts`, `src/core/fake-store.ts`, contract tests in `src/core/store-contract.ts`.
- [ ] Red tests (contract, both stores):
  - `addTags` attaches only missing keys, returns them in order; existing tags keep name, source, kind (an inferred project stays an inferred project); a tag added by another writer before the call is kept;
  - all keys present: nothing written, `added` empty, and an earlier edit's `undoEdit` still answers `"undone"`;
  - absent, foreign and deleted links: null, nothing written;
  - a tag added this way is found by tag filter / search and listed in the owner's tag names.
- [ ] Red tests (savePage): a new link saved with tags has them `stated`, in order, deduped by key; a repeat save answers `tagsAdded` and `tagsHad` (typed tags only); a repeat save with a why and tags applies both.

### Task 2: Route

**Files:** `src/web/http.ts` (`saveBody`, the `SAVE_PATH` POST, `savedJson`); tests beside the existing save-route tests (find with `grep -rln "SAVE_PATH" src/web --include='*.test.ts'`).

- `saveBody.tags`: optional array of texts, each at most `EDIT_MAX_TAG_TEXT`; otherwise 400 `invalid_input`.
- [ ] Red tests: tags saved on a new link and answered; repeat save answers `tagsAdded`/`tagsHad`; bad shapes are 400 with nothing saved; `src/mcp/isolation.test.ts` still passes (no new route).

### Task 3: Dialog

**Files:** `src/web/save-dialog.ts`, `src/web/edit-dialog.ts` (move the picker out), a new `src/web/tag-picker.ts`, `src/web/theme.ts` only if needed; tests `src/web/save-tags.test.ts` (new, model on the save dialog's page tests) and the edit dialog's existing tag tests unchanged.

- Extract Edit's tag picker (chips, x, suggestions from `/tags/names`, Enter adds, typed text added on Save, `keyOf`, `addTag`) into one script factory in `tag-picker.ts` used by both dialogs; Edit keeps its behaviour (its `openedTags`/guess handling stays Edit's, passed in).
- Save dialog: a `Tags (optional)` fieldset under the why, same classes as Edit's so the theme applies; names load on open; Save sends `tags` (names, including what's left in the box) only when there are any; `reset` empties them.
- Cards on the page: after a repeat save that added tags, every card of that link on the page shows its new tags, space and colour and carries the new `data-tags`, so Edit link opened next uses the current tags (no stale `seen` conflict). The answer carries what Edit's own redraw needs (the edit route's `cardState` for that link); the dialog hands it to the same redraw Edit uses after its Save, not a copy. This is the mockup's "every card for the link shows … its space and color at once".
- Found view: the note names what was added and what it had, as the mockup: "Added your tags: a, b. It already had c." (only the parts that apply).
- [ ] Red tests: picker in Save (suggest, Enter, x, leftover text on Save); posts `tags`; found note wording for added-only, had-only, both; reset clears chips; Edit's tag tests still pass unchanged.
- [ ] Browser check: desktop and 390px phone, light and dark, S1 and while typing.
- [ ] Docs: README (Save takes tags), `src/web/AGENTS.md` if the picker sharing is a rule, ROADMAP decision-log `2026-11-20, #352`.

## Review focus

1. A repeat save never drops or relabels a tag the link already had, even with a concurrent change, and never leaves a typed tag unsaved while answering success.
2. A repeat save leaves an earlier edit's Undo working.
3. After a repeat save, the page's cards and their edit data are current.
4. Nothing is written when every typed tag is already there.
5. Edit link's tag behaviour is unchanged after the picker moves.
6. `/save` (bookmark page) still reads no owner data on its GET.
